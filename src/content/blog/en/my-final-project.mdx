## Introduction

As the final monograph project for the Postgraduate Diploma in Information and Technology Security—which simultaneously served as the dual-degree graduation modality to obtain my B.Sc. in Systems Engineering—I conducted an authorized penetration testing assessment of the SISGAA web system at Universidad Mayor de San Simón (UMSS) in 2024. The project applied industry-standard methodologies from **OWASP Top 10:2021** and **OWASP API Security Top 10 (2023)** to identify, analyze, and recommend mitigations for security vulnerabilities.

> **Note:** You can view the complete academic monograph in the <a href="http://atlas.umss.edu.bo/handle/123456789/47539" target="_blank" rel="noopener noreferrer">UMSS institutional repository</a>. All findings described below reflect a point-in-time academic security evaluation conducted in 2024 in a controlled setting and delivered to the institution with remediation guidelines; they do not describe the current state of any live system.

## Project Background

The SISGAA (Sistema de Gestión Académica y Administrativa) system is a web application used by the Department of Computer Science and Systems. Because it handles academic and administrative workflows, evaluating its security posture under established international standards was essential for strengthening institutional software quality.

## Methodology

My approach followed a structured penetration testing methodology:

1. **Planning and Scope Definition**: Established clear boundaries and objectives for the authorized security assessment
2. **Information Gathering**: Collected data about the system architecture and technology stack
3. **Vulnerability Analysis**: Identified potential security weaknesses against OWASP benchmarks
4. **Exploitation**: Verified vulnerabilities through controlled testing
5. **Documentation**: Detailed findings and remediation recommendations for the development team

## Technical Approach

The penetration testing process incorporated the two latest OWASP standards available at the time of the 2024 assessment:

### Web Application Testing (OWASP Top 10:2021)

I conducted tests aligned with the **OWASP Top 10:2021** categories, focusing on:

- **A03:2021 – Injection (including Cross-Site Scripting / XSS)**
- **A07:2021 – Identification and Authentication Failures**
- **A02:2021 – Cryptographic Failures** (sensitive data exposure in transit or storage)
- **A05:2021 – Security Misconfiguration**
- **A06:2021 – Vulnerable and Outdated Components**

### API Security Testing (OWASP API Security Top 10 – 2023)

Because modern web applications rely heavily on REST APIs, I paired web testing with the **OWASP API Security Top 10 (2023)** methodology:

1. **Discovery**: Mapping the API structure and endpoints (**API9:2023 – Improper Inventory Management**)
2. **Endpoint Analysis**: Examining request/response patterns and configuration (**API8:2023 – Security Misconfiguration**)
3. **Authentication Testing**: Verifying login and token mechanisms (**API2:2023 – Broken Authentication**)
4. **Authorization Verification**: Testing object- and function-level access control boundaries (**API1:2023 – Broken Object Level Authorization** and **API5:2023 – Broken Function Level Authorization**)

## Key Findings (2024 Point-in-Time Assessment)

During the 2024 evaluation, the assessment identified the following categories of weaknesses for remediation:

1. **Reflected Cross-Site Scripting (OWASP A03:2021)**: Insufficient output encoding on specific parameters allowed reflected script execution in controlled test cases
2. **Broken Object Level Authorization (OWASP API1:2023)**: Missing object-level ownership checks on certain API endpoints
3. **Broken Function Level Authorization (OWASP API5:2023)**: Insufficient role verification on privileged endpoints
4. **API Documentation Exposure (OWASP API8:2023 / API9:2023)**: Publicly accessible Swagger specification endpoints
5. **Missing HTTP Security Headers (OWASP A05:2021)**: Absence of restrictive browser security headers such as `Content-Security-Policy` and `X-Frame-Options`
6. **Vulnerable and Outdated Client Libraries (OWASP A06:2021)**: Use of frontend JavaScript dependencies with known advisories

## Technical Implementation

The project utilized specialized security tools:

- **OWASP ZAP**: For automated vulnerability scanning
- **Burp Suite**: For intercepting and analyzing HTTP requests
- **Custom Scripts**: For testing API authorization boundaries
- **Browser Developer Tools**: For analyzing client-side application behavior

## Impact and Mitigation

For each finding documented in the 2024 report, I provided concrete remediation strategies:

- **Input Validation and Context-Aware Output Encoding**: To prevent XSS and injection vectors
- **Granular Authorization Checks**: To enforce object- and function-level access control on every API route
- **API Surface Hardening**: To restrict specification endpoints to non-production environments
- **Security Header Implementation**: To enforce defense-in-depth browser policies
- **Dependency Lifecycle Management**: To audit and update third-party libraries continuously

## Conclusion

This project demonstrated how systematic penetration testing grounded in **OWASP Top 10:2021** and **OWASP API Security Top 10 (2023)** can surface architectural and configuration weaknesses early so engineering teams can remediate them. Above all, the work underscored the importance of integrating security controls throughout the software development lifecycle.
